# Bank data enters through canonical contracts; scales stay bank codes

The app is built in an external cloud environment that cannot reach the bank, then cloned into an internal environment where the bank's APIs live (the CRM, a GraphQL API with `portfolio` and `person` queries; FMD for instruments and their documents). So the app reads bank data only through out ports whose models we define ourselves ([Client Profile](../playbook/contracts/client-profile.md), [Share Classes](../playbook/contracts/share-classes.md), [Fund Documents](../playbook/contracts/fund-documents.md), [Fund Registrations](../playbook/contracts/fund-registrations.md)), each with a fixture adapter and a bank adapter. **The adapter is chosen per port, not per environment**: inside the bank, a port whose bank data is not usable keeps its fixture or folder adapter. No REST endpoint sits between the app and its adapters, and nothing above a port knows the bank's schema or protocol: moving inside the bank means writing the bank adapters and nothing else.

Inside the contracts, the bank's **scales** (risk profile, knowledge and experience, ability to bear losses) are passed through as bank codes and translated only by the validated Scale Mapping, because translating them is a judgement someone must check, and it must change with the bank's real scales without code. **Legal categories** (Investor Classification, opting declarations, mandate type) become canonical enums in the bank adapter, because they are closed lists set by law that rules branch on directly. Every fact is optional: absent means unknown, unknown gives Review, and adapters never fill defaults.

**Amended 2026-10-24: adapters per port.** The internal environment we reach at the event is the bank's DEV environment. There, FMD's instrument data, document metadata and registration data are real, but its document PDFs and the CRM's client data are mocks, and we can't reach TEST or UAT. So at the event `ShareClasses` and `FundRegistrations` read DEV FMD, while `FundDocuments` reads a folder of real PDFs (its manifest generated from FMD's metadata) and `ClientProfiles` reads the demo fixtures, which are the coverage set's answer key. The FMD document adapter and the CRM GraphQL adapter are specified but not built. In production they replace the folder and fixture adapters, and nothing else changes. Only out-port adapters switch: the Privacy Gate and the LLM egress client are the same in every environment.

## Considered Options

- **Guess the bank's GraphQL schema and mock it outside**: the adapter would look written early, but a guessed schema would almost certainly be wrong and get rewritten at the event anyway.
- **A small REST facade serving the contract, mocked outside, real inside the bank**: the app would be one build moved by a URL, but it adds a deployable for a 20-hour build, and only the adapter's code differs between the two environments either way.
- **Bank adapter translates the scales too**: one place for all mapping, but it would bury a validated, regulatory correspondence in code no validator reads.
- **One Spring profile per environment** (the first version of this ADR): simple, but in DEV it would make a Rule Card from a mock PDF and Verdicts on mock clients with no answer key.
- **Build the CRM and FMD document adapters against DEV's mocks anyway**: proves the plumbing, but costs event hours on something no one sees, and a mock PDF fed by mistake gives a nonsense card.
